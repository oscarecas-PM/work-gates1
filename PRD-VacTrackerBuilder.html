Product Requirements Document (PRD)

Product Name: True-VAC Tracker Builder

File: vac-tracker-builder-1.html

Version 1.1 | June 2, 2026 | Author: Oscar Castillo

1. Overview

A client-side, one-shot tool that rebuilds the VAC Tracker Log from a batch of historical P-Files, so the user does not have to load P-Files into the Gate Tracker one week at a time. For each P-File (dated from cell C3) the tool pairs the same-dated Daily Upload and a single Decoder Ring, computes Earned-Value metrics per work order using the exact Gate Tracker EVM formula, and emits a CSV in the exact format Gate Tracker's exportVacLog() produces (Date, WO, Part #, VAC, CPI). The output is intended to be byte-identical, for any matching (Date, WO), to what the Gate Tracker EVM report would compute for that date.

v1.1 adds a data-integrity layer: it detects and quarantines truncated Daily Uploads (partial files pulled during the MES midnight refresh, which undercount operations and inflate VAC), and it audits an existing VAC tracker / old Gate Tracker snapshots for rows already polluted by that defect. See §6.4–§6.5 and §11.7–§11.9.

This tool exists because of a root-cause finding (2026-06-02): the VAC stored in the tracker is not a pure-P-File quantity. It carries an ETC term whose operation statuses come from the live Daily Upload, so a month-old P-File replayed against a different day's Daily Upload yields a different VAC. The stored "historical" VAC was therefore always a hybrid of a dated P-File and whatever Daily Upload happened to be loaded that day — not reproducible. This tool restores reproducibility by pairing each P-File with the Daily Upload of its own date.

2. Objectives

  • Rebuild the VAC tracker for many historical dates in a single pass, eliminating the one-week-at-a-time manual loop through the Gate Tracker.
  • Produce VAC and CPI values that are identical to the Gate Tracker EVM report for the same inputs — achieved by porting the Gate Tracker's parsers and EVM math verbatim (not re-deriving them).
  • Match the exact output schema of exportVacLog() (Date, WO, Part #, VAC, CPI) so merging is a plain text operation with no schema changes anywhere else.
  • Pair each P-File to its contemporaneous Daily Upload so the ETC term reflects the operation statuses as of the P-File's date, not "today".
  • Surface a complete picture of what was and was not built — date pairing, omitted work orders, Decoder Ring coverage, and data-quality anomalies — before the user merges anything.

3. Architecture Constraints

  • Entirely client-side; all parsing, computation, and CSV generation happens in the browser.
  • Single self-contained HTML file with embedded libraries (no CDN).
  • No persistent storage (no cookies, localStorage, IndexedDB).
  • Must work in modern browsers (Chrome, Edge).
  • Same security envelope as the rest of the suite: esc() XSS prevention on dynamic HTML, CSP meta tag, CSV field quoting + length cap.

5. Data Inputs

5.1 P-Files (.xlsx, required, multiple)

Peabody cost-system exports — one per program per date. Identical parse path to Gate Tracker (PRD-GateTracker.html §3.6). The "as of" date is read from cell C3 (format As of M/D/YYYY). The header row is auto-detected by scanning the first 10 rows for a cell whose trimmed value equals WO (case-insensitive). Each file keeps its own C3 date (the tool does NOT take the minimum across files, unlike Gate Tracker which merges programs at a single date).

ColumnTypeUse
WOStringWork order identifier; primary key. Rows with blank WO or Total / Totals / Grand Total are skipped; parsing stops at two consecutive blank rows.
BaselineNumericProgram EAC (originally budgeted hours).
Total Actual HoursNumericCumulative hours charged to the WO to date.
Percent CompleteNumericWO completion. Decimal 0–1 is normalized to 0–100 exactly as Gate Tracker does (n ≤ 1 && n > 0 ? n×100 : n). Do not "fix" this — it must stay identical so VAC/CPI match.
Part NumberString (optional)Read by header name when present and emitted as Part #. When absent (e.g. the dummy fixtures), the tool falls back to the Daily Upload part. See F-06.

Multi-file ingest is per-file try/catch via FileReader — one bad file does not abort the batch; failures are recorded per-file in the status line. Missing required columns produce a per-file warning, not a hard error.

5.2 Daily Uploads (.csv, required, multiple)

MES snapshots (tab-delimited despite the .csv extension; the ported parseCSV() auto-detects the delimiter). Identical column semantics to PRD-GateTracker.html §3.2. The Daily Upload has no internal date column — the snapshot date is parsed from the filename (see F-03).

ColumnTypeUse
Order NoStringWO identifier; joins to the P-File WO.
Operation NoString4-digit with leading zeros (e.g. 0030); normalized via normOper() to match the Decoder Ring's bare numbers.
Operation StatusStringACTIVE / IN QUEUE / PENDING drive the ETC sum.
Part NumberStringUsed as the Decoder-Ring lookup key namespace (and as the Part # fallback).

Only these four columns are required. Other Daily Upload columns are ignored. Rows are grouped into a per-WO lookup (byOrder).

5.3 Decoder Ring (.csv, required, exactly one)

One current Decoder Ring supplying per-operation labor hours for the ETC term, reused across all P-File dates. Same EVM columns as PRD-GateTracker.html §3.9 / PRD-DecoderRingBuilder.html.

ColumnTypeUse
Part No.StringLookup key (with Oper No.).
Oper No.StringBare op number; normalized via normOper().
Labor HoursNumericPlanned hours per operation. Only values > 0 are stored.
Earnable Hours FlagString (optional)Operations with flag N are excluded from ETC. When the column is absent, the flag defaults to Y and the tool warns that all positive Labor Hours are treated as earnable.

The lookup is keyed partNo + '|||' + normOper(operNo), identical to Gate Tracker's laborHoursLookup.

5.4 Existing VAC Tracker / GT Snapshots (.csv, multiple, optional — v1.1)

The user's current VAC tracker and/or previously-generated Gate Tracker report snapshots, in exportVacLog format (Date, WO, Part #, VAC, CPI). Parsed with the ported parseCSV/colIndex; rows with a blank/non-numeric VAC or unparseable date are skipped (counted). When present, this input drives the audit (§6.5).

5.5 Integrity settings (v1.1)

Two action-bar controls: a truncation sensitivity number input (default 0.6 — flag a Daily Upload whose op-row count is below this fraction of the batch median) and a known-bad dates textarea (one M/D/YYYY per line) for manual force-quarantine.

6. Functional Requirements

6.1 Computation

F-01 For each P-File record, find the Daily Upload whose filename-parsed date equals the P-File's C3 date. If none exists, the entire P-File's work orders are omitted (see F-07) and the date is reported in the completeness panel.

F-02 For each WO present in both the P-File and that date's Daily Upload, compute the EVM metrics using the formula ported verbatim from gate-tracker-34.html:2505–2524:

programEAC    = Baseline (P-File)
ETC          = Σ Decoder Labor Hours for ops in {ACTIVE, IN QUEUE, PENDING}, Earnable Flag ≠ N
productionEAC = Total Actual Hours + ETC
VAC          = programEAC − productionEAC
EV           = (Percent Complete / 100) × programEAC
CPI          = Total Actual Hours > 0 ? EV / Total Actual Hours : (blank)

F-03 Daily Upload date from filename. parseDateFromFilename() tries, in order: YYYY-M-D (any of - _ . space separators), M-D-YYYY (US default), YYYYMMDD (plausible 20xx year), MMDDYYYY. Out-of-range month/day yields no date. When a separated/8-digit form is genuinely ambiguous (both leading numbers ≤ 12 and unequal), the file is flagged ambiguous in the status line so the user can verify. Files with no parseable date are omitted and reported.

F-04 Operation-number normalization. normOper() (ported, strips leading zeros) is applied on BOTH sides of the Decoder-Ring lookup key, so Daily Upload 0030 matches Decoder Ring 30. The ETC lookup uses the Daily Upload part number (the namespace the Decoder Ring shares), matching Gate Tracker line 2503/2511.

F-05 Dedup, sort, format. Output is keyed (Date, WO); on a same-key collision the last record wins and the collision is counted. Rows are sorted Date ascending, then WO ascending, using the exact comparator from gate-tracker-34.html:5173–5180. Each row is emitted as Date, WO, Part #, VAC.toFixed(2), CPI.toFixed(3) (CPI blank when null), matching exportVacLog() lines 5182–5192. The Part # field is passed through csvCell() (comma/quote-safe); all other fields are inherently delimiter-free.

F-06 Part # source. The output Part # is the P-File "Part Number" value when that column is present and non-empty; otherwise it falls back to the Daily Upload part for that WO. When the two are both present and differ, the row uses the P-File value for Part # and the Daily Upload value for the ETC lookup, and the mismatch is reported in the panel.

F-07 Omission policy (user decision). A (Date, WO) row is omitted entirely — no VAC, no CPI — when (a) the P-File's date has no matching Daily Upload, or (b) the WO is absent from that date's Daily Upload. Rationale: true VAC cannot be computed without ETC, and a CPI-only row would be dropped by Gate Tracker on import anyway (a blank/non-numeric VAC row is skipped at gate-tracker-34.html:2429). Every omission is counted and listed.

6.2 Output

F-20 A preview table renders the first 50 emitted rows (Date, WO, Part #, VAC, CPI), with VAC and CPI right-aligned. Blank CPI is shown as a muted em-dash.

F-21 "Download VAC Tracker CSV" writes the exportVacLog-format CSV. Filename: vac-tracker-log-YYYY-MM-DD.csv (matching Gate Tracker's own download name). The download button is hidden until a build produces at least one row.

F-22 The "Build VAC Log" button is enabled only when at least one P-File parsed with ≥ 1 WO, at least one Daily Upload has a parsed date, and a Decoder Ring with ≥ 1 earnable operation is loaded.

6.3 Completeness Panel

F-30 After each build, a completeness panel reports every count below. This is a hard requirement — per the suite-wide rule that any aggregation over potentially-sparse data must show coverage/omission explicitly (see memory/feedback_surface_data_completeness.md):

  • Inputs: P-Files parsed (files + distinct dates), Daily Uploads with a parsed date, Decoder Ring earnable op count.
  • Date pairing: P-File dates matched to a Daily Upload vs. total; each unmatched date listed with its omitted-WO count.
  • Omissions: WOs omitted for being absent from that date's Daily Upload, each listed.
  • ETC / Decoder coverage: Active/In-Queue/Pending ops matched to a Labor Hours entry vs. total, as a percentage; amber below 80%, with the top unmatched part|||op keys listed (ETC is understated for these).
  • Data quality: Part # missing on emitted rows; P-File vs Daily-Upload part mismatches; duplicate (Date, WO) collisions resolved last-wins; rows with blank CPI (Total Actual Hours = 0).
  • Output: total rows emitted; distinct dates in output.

6.4 Daily Upload truncation detection & quarantine (v1.1)

A mid-refresh Daily Upload is a partial file (fewer ops → ETC undercounted → VAC inflated). computeDuIntegrity() runs over the loaded batch before buildVacRows and quarantines suspect dates.

F-40 Global outlier (primary). Compute the batch median op-row count across all Daily Uploads; flag any DU whose row count is below median × factor (factor from the sensitivity control, default 0.6). Matches the whole-file failure mode (the dashboard writes a partial file, so the entire pull is short).

F-41 Per-WO monotonicity dip (secondary). A WO's active-op count only ever declines over its life (closed ops drop out of the Daily Upload). For each WO, any date whose op count is below a later date's count is an impossible rebound → that DU is truncated for that WO. A date is dip-quarantined when at least DIP_MIN_WOS (default 2) WOs show the rebound, reducing false positives from a lone re-opened op.

F-42 Manual override. Dates pasted into the known-bad-dates box are force-quarantined. The panel reports manual-vs-auto agreement: which manual dates the detector also caught, manual-only dates (the detector missed), and auto-detected dates beyond the user's list.

F-43 Quarantine handling. A quarantined date's rows are omitted entirely from the build (routed to omissions.quarantined with reasons), mirroring the no-Daily-Upload omission path. Quarantine, not substitution (user decision; substitution is out of scope for v1.1). The completeness panel adds a "Daily Upload integrity" section (median, quarantined dates + reasons, below-median-but-kept DUs, manual/auto agreement) and the omitted-rows count.

F-44 Suspect Daily Uploads report. A downloadable CSV lists every DU with its op-row count, % of median, quarantine flag, and reasons. Filename suspect-daily-uploads-YYYY-MM-DD.csv.

6.5 Audit of an existing tracker (v1.1)

Active only when input 5.4 is provided.

F-50 Flat-CPI / VAC-jump scan. Group old rows by WO, sort by date; flag the later row of any consecutive pair where |ΔCPI| ≤ CPI_EPS (0.02) and ΔVAC ≥ VAC_JUMP (5h). This is the already-polluted-row signature (ETC fell with no cost/progress change), the same rule as the Gate Tracker live guard.

F-51 Rebuild-vs-old diff. Compare the clean rebuild to the old tracker per (Date, WO): classify corrected (|Δvac| ≥ 0.5h), removed (in old, not in rebuild — distinguishing "date quarantined" from "no P-File/DU match or WO absent"), new, and unchanged.

F-52 Audit report. Panel section summarizing F-50/F-51 plus a downloadable multi-section CSV (suspect / corrected / removed / new). Filename vac-audit-YYYY-MM-DD.csv.

11. Design Decisions & Notes

11.1 Why this tool exists — VAC is not a pure-P-File quantity

Investigation on 2026-06-02 (see memory/investigation_vac_delta_root_cause.md) traced an across-the-board positive ΔVAC in the Manager EVM report to the structure of the VAC formula. CPI is fully P-File-derived (%Complete × Baseline / Actual), but VAC includes an ETC term whose operation statuses come from the live Daily Upload. As ops close week-to-week, ETC falls and VAC = Baseline − (Actual + ETC) rises — even when Baseline and Actual are unchanged. The user confirmed by re-opening a month-old P-File: identical Baseline/Actual, different VAC. The stored historical VAC was always a hybrid of a dated P-File and whatever Daily Upload was loaded, so it was never reproducible. This tool fixes that by pairing each P-File with the Daily Upload of its own date.

11.2 Verbatim port over re-implementation (decision, v1.0)

The P-File parser, parseCSV, colIndex, normOper, the Decoder-Ring labor-hours lookup, the byOrder build, the EVM math, and the output formatter/sort are all ported verbatim from gate-tracker-34.html rather than re-derived. This is deliberate: the entire value of the tool is that its numbers match the Gate Tracker exactly, so any independent re-implementation would be a liability. PapaParse was rejected for the same reason — Gate Tracker uses its own parseCSV, so the tool does too.

11.3 Date from filename (decision, v1.0)

The Daily Upload has no internal date (PRD-GateTracker §3.2 — it is a daily snapshot paired by processing date). To rebuild historical VAC, each P-File must be paired with the Daily Upload from its own date, so the tool reads the date from the filename. US M/D ordering is the default for ambiguous separated forms; ambiguous files are flagged for the user to confirm. This depends on the user having archived Daily Uploads with dated filenames — see §11.5.

11.4 Omit, don't proxy (user decision, v1.0)

When ETC cannot be computed (no matching Daily Upload, or WO absent from it), the row is omitted entirely rather than emitted with a proxy or blank VAC. The user chose this explicitly. It is also the only honest option for Gate Tracker import: a blank/non-numeric VAC row is silently skipped on import (gate-tracker-34.html:2429), so a CPI-only row would not populate the tracker anyway. Contrast with vac-backfill-tool-1.html, which deliberately writes blank VAC because it is a different (earned-vs-actual CPI proxy) pipeline; see PRD-VacBackfillTool.html §11.4.

11.5 Reproducibility limit — requires same-dated Daily Uploads

Because VAC depends on the Daily Upload's operation statuses, faithful historical VAC requires the Daily Upload from each historical date. If the user has not archived old Daily Uploads, CPI will still be exact (it is pure-P-File), but historical VAC cannot be perfectly reconstructed. This is a property of the Gate Tracker's VAC definition, not a defect of this tool.

11.6 Relationship to the VAC Tracker Backfill Tool

This tool and vac-backfill-tool-1.html both emit the exportVacLog schema but are distinct. The Backfill Tool computes a CPI proxy (cumulative earned ÷ cumulative actual) from tech-charge .xlsx + Hours Earned, for periods with no P-File coverage, and writes blank VAC. This Builder uses real P-Files + the Daily Upload + the Decoder Ring to compute the true ETC-based VAC and the true Gate-Tracker CPI. Use the Builder when P-Files exist for the period; use the Backfill Tool only when they do not.

11.7 Truncation root cause & the detection signature (v1.1)

Oscar traced the persistent VAC fluctuation to the MES dashboard's midnight refresh: a Daily Upload downloaded mid-refresh is a partial file. Because closed operations drop out of the Daily Upload, a WO's active-op count is monotonically non-increasing, so a partial pull shows fewer ops than reality (one WO seen at 16 ops dropped to 8). Fewer ops → ETC undercounted → VAC inflated — even though the P-File never moved. He confirmed it affects multiple dormant WOs in the same windows (whole-file truncation) and noted the specific bad dates back to March. The detection signature — CPI flat but VAC up — is identical to the Gate Tracker live guard (see PRD-GateTracker.html §4.9.2 F-230/F-231).

11.8 Quarantine, not substitution (decision, v1.1)

A flagged date's rows are omitted, not reconstructed from a neighbor Daily Upload. Substitution was considered (the daily cadence usually provides a healthy neighbor within 1–3 days) but rejected for v1.1: operation statuses shift day-to-day, so a substituted VAC would be approximate, and the user preferred a clean omission they can re-pull. Revisit once detection is trusted.

11.9 Two detectors, layered (decision, v1.1)

The global median-outlier test (F-40) is the primary guard because the observed failure is whole-file. The per-WO monotonicity dip (F-41) is a precision complement for the rarer case where a file isn't globally short but a WO's op count rebounds. The known-bad-dates box (F-42) both lets the user force a quarantine and serves as ground truth: the panel reports whether the auto-detector independently caught the dates the user already identified. Verified 2026-06-02: global-outlier catches a whole-file 29%-of-median truncation; the dip detector independently catches a mild (91%-of-median) drop-and-rebound across 2 WOs; the audit flags a planted flat-CPI/VAC-jump pair while leaving a clean progression untouched; a healthy cohort yields zero quarantines and the unchanged v1.0 ground-truth output.

12. Out of Scope

  • Auto-substitution of a healthy neighbor Daily Upload. Quarantine-only for v1.1 (see §11.8).
  • Merging the output into the live VAC tracker. The user concatenates externally.
  • Changing the Gate Tracker's VAC definition. Whether the Gate Tracker itself should pair a dated P-File with a same-dated Daily Upload (rather than the live one) is a separate methodology decision logged against gate-tracker-34.html; this tool does not modify the Gate Tracker.
  • Operation-level VAC/CPI. WO-level only, matching Gate Tracker.
  • Trend visuals / comparison panel. This tool emits CSV + a completeness panel only; trend visualization happens downstream (Gate Tracker, EHA) after merge.
