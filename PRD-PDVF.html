1. Executive Summary

Aerospace and defense manufacturing programs rely on complex, multi-level work order trees where parts, materials, calibrated equipment, and certified personnel must converge at precisely the right moment. Today, that convergence is managed through tribal knowledge, disconnected spreadsheets, and reactive expediting — a pattern that generates avoidable cost and delivery risk.

The Production Dependency & Velocity Forecaster (PDVF) is a shop floor intelligence tool that maps work order dependency trees up to five levels deep, projects forward completion dates using earned-hour velocity, and generates actionable demand signals for every resource category — materials, purchased parts, equipment, and personnel certifications — across 30, 90, and 180-day planning horizons.

A proof-of-concept prototype has been developed in-house using the FabLab's digital tooling capability and is available for demonstration. This document defines the requirements for a production-grade web application to be funded, built, and integrated with the organization's Manufacturing Execution System (MES).

PROBLEMWe do not know when we will need what until it is too late. The result is expedite fees, overtime, and delivery risk that is entirely predictable — but currently invisible.
SOLUTIONPDVF makes the invisible visible: a real-time, velocity-driven forecast of every resource dependency across every active work order, surfaced at the right time for the right decision-maker.

2. Problem Statement

2.1 The Dependency Blindspot

A complex aerospace assembly may require 100 or more work orders that tier into one another across five or more levels. Each work order contains a sequenced build flow — organized by production gates — and each gate may require specific materials, purchased components, calibrated equipment, and personnel holding current process certifications.

The work order system (MES) captures this structure, but it has no mechanism to answer the following questions:

  • When will operation X on work order Y reach gate G?
  • What resources does gate G require, and when must they be ready?
  • If work order A slips, which downstream work orders are affected and by how much?
  • Which feeder work orders are on the critical path to the top-level delivery date?

2.2 The Velocity Problem

MES start and end dates are set at work order creation but are rarely updated when milestones are missed. Over time, planned dates become fiction. There is no current mechanism to derive a data-driven projected completion date from actual production activity — specifically, from the rate at which earned hours are being closed across work order operations.

2.3 The Resource Readiness Gap

Functional owners — materials planners, equipment coordinators, certification managers — have no forward-looking demand signal. They respond to requests when work is about to begin, not when lead times demand action. The result:

  • Materials are ordered too late, triggering expedite fees
  • Equipment certification lapses are discovered when the work order reaches that gate
  • Personnel certifications expire before they are needed, requiring unplanned training cycles
  • Purchased parts with long lead times are not on order until shortages are visible
IMPACTThe inability to forecast resource demand against a realistic production schedule generates reactive, high-cost responses to problems that were entirely predictable weeks or months in advance.

3. Product Vision

PDVF is a production intelligence layer that sits alongside the MES, reads its data, and surfaces what the MES cannot: a time-projected, dependency-aware, resource-enriched view of the entire production program.

The tool does not replace the MES. It does not manage work orders, issue travelers, or record labor transactions. Its purpose is singular: to tell each stakeholder what they need to know, when they need to know it, so they can act before the problem arrives.

3.1 North Star Statement

"Any resource owner — materials, equipment, certifications — can open PDVF on any Monday morning and know exactly what they need to have ready in the next 30 days, what they need to order or initiate in the next 90 days, and what long-lead items are at risk over the next six months — all derived from actual production velocity, not planned dates that no one maintains."

5. Functional Requirements

5.1 Dependency Map Editor

The dependency map is the structural foundation of the system. It must support the following:

5.1.1 Part Structure Templates

  • Define a reusable part structure template: which part number kits into which parent, at which gate, at which level of the hierarchy
  • Support up to five levels of nesting (Level 0 = top-level assembly; Level 4 = deepest feeder component)
  • Templates are stable across releases — the structure of how parts relate does not change when work order numbers change
  • Templates must be editable to accommodate Engineering Change Orders (ECOs)

5.1.2 Work Order Assignment

  • Each release, a planner or program engineer assigns specific work order numbers to each node in the template
  • Assignment is a best-estimate — the tool must allow reassignment up to the moment of kitting
  • The system must log who made each assignment and when (audit trail)
  • Multiple work orders may feed into the same parent node; each carries its own gate join point

5.1.3 Gate Join Points

  • Each feeder work order specifies which gate on the parent work order it must be ready for
  • A join at Gate 1 means the feeder must be complete before the parent can begin remaining work
  • A join at Gate N means the parent can continue earning hours on earlier gates while the feeder completes
  • If a parent work order has already earned hours, a Gate 1 join points to the start of remaining forecast work, not the historical start

5.2 Velocity Engine

The velocity engine is the forecasting core of the system. It derives projected completion dates from actual production activity rather than planned dates.

5.2.1 Data Ingestion

  • Accept periodic CSV exports from the MES containing: work order ID, total earnable hours, hours earned to date, number of weeks active
  • In the funded build: replace CSV upload with a direct MES database query or API call
  • Each upload creates a timestamped velocity snapshot retained for trend analysis

5.2.2 Velocity Calculation

  • Daily rate = earned hours / (weeks active × 5 working days)
  • Remaining work = total earnable hours − earned hours to date
  • Days to completion = remaining work / daily rate
  • Projected completion date = today + days to completion

5.2.3 Cascade Logic

  • When a feeder work order's projected completion date shifts, the system recalculates the gate entry date on the parent
  • If the feeder will finish after the parent's gate entry date, the parent's effective resume date is pushed to the feeder's projected completion
  • This cascade propagates automatically up all levels of the dependency tree
  • The system iterates until the tree reaches a stable state (convergence)

5.2.4 Purchased Part Blocking

  • A purchased part marked as blocking START prevents the work order's remaining work from beginning until the ECD has passed
  • Work already earned is displayed as historical and is not recalculated
  • A purchased part blocking a specific gate delays that gate's commencement, not the entire work order
  • Part blocks cascade into the parent tree through the same mechanism as feeder WO delays

5.3 Critical Path View (Primary View)

A Gantt-style visualization where time runs left-to-right on a shared calendar axis and each work order occupies one row.

5.3.1 Bar Representation

Each work order is represented by two bars on the same row:

  • Left bar (solid border): earned work to date. Spans from work order start to today. Width reflects hours closed; gate segments show completed gates.
  • Right bar (dashed border): forecast remaining work. Starts at ECD of blocking part (or today if unblocked). Ends at velocity-projected completion date.
  • Gap between bars: the blocked wait period. Labeled 'waiting' if space permits.
  • A purple diamond marker above the bar indicates the original planned end date
  • A red slip indicator below the bar shows the number of days of delay when projected > planned

5.3.2 Gate Segments

  • Each bar is subdivided into gate segments proportional to the total number of gates
  • Completed gates are displayed with higher visual weight on the left bar
  • Forecast gates are displayed at reduced opacity on the right bar

5.3.3 Dependency Connectors

  • Dependency lines connect feeder work order projected completion to the gate entry point on the parent
  • Routing: straight vertical line from feeder bar end, underpass (horizontal run just below parent bar bottom), then rises into parent bar with upward arrowhead
  • Red solid line = critical path (float ≤ 14 days)
  • Amber dashed line = at risk (float 15–30 days)
  • Dark dashed line = healthy (float > 30 days)
  • Connectors never cross through bars; they route underneath using the underpass pattern

5.3.4 Purchased Parts (Inline)

  • The longest-lead purchased part for each work order is displayed below its bar row by default
  • An expand control reveals the full purchased part list for that work order
  • Each part shows: description, ECD on the timeline, and blocking label (START or Gate N)
  • Overdue parts (ECD in the past) are highlighted in red

5.4 Gate Loading Matrix

A matrix view for staffing and gate assignment decisions, separate from the critical path view and intended for shop floor supervisors.

  • Gates as columns; time horizons (30-day, 90-day, 6-month) as rows
  • Each cell displays: work order count, total earnable hours, implied headcount (hours / 160 hrs per person per month)
  • Load bar per cell: color-coded green/amber/red based on hours as a percentage of gate capacity
  • Expanding a row reveals required certifications per gate and the number of work orders requiring each cert
  • A totals column shows program-level roll-up per horizon

5.5 Resource Demand Forecast

A role-filtered demand summary for materials and equipment planners, organized by 30/90/180-day horizons.

  • Materials section: resource name, quantity needed, number of driving work orders, unit of measure
  • Equipment section: equipment name, days of reservation needed, number of driving work orders
  • 6-month horizon filtered to long-lead items only — non-long-lead items dimmed
  • Separate views filterable by resource type so each functional owner sees only their domain

5.6 Purchased Parts Tracker

A dedicated interface for procurement and materials personnel to maintain ECD data for purchased parts.

  • Add purchased parts to any work order node in the dependency tree
  • Set and update ECD per part
  • Mark each part as blocking START or blocking a specific gate number
  • View all parts across all work orders sorted by ECD urgency
  • Flag parts as ordered, received, or at-risk
  • Changes to ECDs automatically recalculate the velocity cascade and update all dependent projected dates

5.7 Portfolio Roll-up (Phase 2)

  • Summary view across all active programs showing: on-time WO count, at-risk count, critical count
  • Click-through to program-level critical path view
  • Aggregate resource demand across programs for shared resource conflict detection

7.2 Relationship Rules

  • One Part Template may have many Work Order Instances across releases
  • One Work Order Instance belongs to exactly one Part Template node
  • A Work Order Instance may have zero to many Purchased Parts
  • A Work Order Instance may have zero to many feeder Work Order Instances (up to 5 levels deep)
  • Velocity Snapshots are append-only; historical snapshots are never deleted

10. Assumptions & Constraints

10.1 Assumptions

  • Each program has a dedicated planner or engineer who will own and maintain the dependency mapping for their program
  • The MES can produce an export of work order earned hours on a weekly basis
  • Gate definitions and associated certification requirements are known and can be entered into the system
  • Purchased part ECDs are available and will be maintained by procurement personnel within the tool
  • The organization's IT infrastructure can host an internal web application with a relational database

10.2 Constraints

  • PDVF is a read layer — it does not write back to the MES or alter work order records
  • Expiration dates for certifications and equipment calibrations are maintained in separate systems; PDVF receives demand signals only — readiness status is outside its scope in Phase 1
  • The tool does not replace the MES scheduler — it augments it with a forward-looking, dependency-aware intelligence layer
  • Phase 0 (PoC) uses mock data; real program data is required beginning in Phase 1

12. Glossary

TermDefinition
Earned HoursLabor hours recorded as completed against a work order operation in the MES
VelocityThe rate at which a work order is earning hours, expressed as hours per day or hours per week, derived from historical performance
GateA defined stage in the production build flow. Work orders progress sequentially through gates.
Gate Join PointThe gate on a parent work order at which a feeder work order's output must be present
FloatThe number of days between a feeder work order's projected completion and the gate entry date on the parent. Negative float = late.
Critical PathThe chain of work orders with the least float to the top-level assembly completion date
ECDEstimated Completion Date — the date by which a purchased part is expected to be received
Velocity SnapshotA point-in-time record of a work order's earned hours used to calculate and track historical burn rates
Part TemplateA reusable definition of how part numbers relate in the dependency tree, independent of specific work order numbers
CascadeThe automatic propagation of a date change through the dependency tree — a feeder slip pushes parent dates, which push grandparent dates, etc.
MESManufacturing Execution System — the shop floor software that manages work orders, operations, and labor transactions
