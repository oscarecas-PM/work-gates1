Product Requirements Document (PRD)

Product Name: Work-Order Hours Earned Bundle Viewer (Earned Hour Analysis)

File: earned-hour-analysis-1.html

Version 1.10 | May 19, 2026 | Author: Oscar Castillo

1. Overview

A client-side web application to upload and process work-order hours earned data along with bundle definitions, presenting detailed tables and visual charts. Supports grouping work orders into bundles with metadata, sorting, and generating printable/exportable reports with charts.

2. Objectives

  • Enable users to upload two required CSV files (hours earned and bundle definitions) plus an optional EV Details CSV and an optional VAC Tracker Log (for CPI overlay)
  • Aggregate earned hours per work order by month, summing across operations
  • Support definition of bundles grouping multiple work orders, with associated metadata
  • Display tabular data grouped by bundle and sorted by part number and order number
  • Visualize data with charts: one series per root part number plus bundle total
  • Provide PDF/print export of tables and charts
  • Provide self-contained HTML snapshot export
  • Hide months prior to the bundle's first earned hours to improve readability
  • Identify unbundled work orders to help users maintain bundle definitions

3. Architecture Constraints

  • Entirely client-side; all processing and chart rendering happens in the browser
  • Single self-contained HTML file with embedded libraries
  • No external server calls; libraries loaded from embedded source (not CDN)
  • No persistent storage (cookies, localStorage, etc.)
  • Must work in modern browsers (Chrome, Edge)
  • Handle large datasets efficiently (36,000+ rows) without crashing or freezing
  • Clean, professional UI styling suitable for aerospace/engineering environments (navy and gray color palette, clear fonts, right-aligned numeric columns)

6.9 Export Bundle Velocity (v1.2)

Revised in v1.2: previously per-WO averages. Capacity throughput is better characterized at the bundle (work-package) level because month-to-month WO earning is noisy (kitting, long-lead parts, cert availability, capacity). Bundle-level velocity aligns with how project managers track delivery commitments.

F-100 "Export Bundle Velocity" button in the action bar, visible after analysis runs.

F-101 Clicking the button reveals an inline settings panel with: lookback months dropdown (3, 6, 9, 12; default 6), exclude current month checkbox (default checked), Download CSV button, Cancel button, and period info label.

F-102 Export includes only bundles defined in the Bundle Definition CSV. Unbundled work orders are excluded (the separate "Export Unbundled CSV" remains for reference).

F-103 Bundle velocity (lookback) = mean of per-month bundle totals across the lookback window. Monthly total = sum of member WO hours for that month. Months with 0 hours count toward the mean (they represent months with no progress).

F-104 Std deviation = population std dev over per-month bundle totals. CV = stdDev / velocity; blank when velocity = 0.

F-104a Bundle velocity (last month) = the bundle's total hours in the single most recent month of the selected window. Provides a "current pace" goalpost independent of the lookback trend. StdDev and CV for the last-month figure are emitted blank (single-sample statistic).

F-105 Two-section CSV:
  Section 1 (one row per bundle): Bundle Name, Program, Lookback Months, Exclude Current Month, Period Start, Period End, Velocity Lookback (hrs/mo), StdDev Lookback, CV Lookback, Month Count Lookback, Last Month, Velocity Last Month (hrs/mo), StdDev Last Month, CV Last Month.
  Section 2 (one row per member WO): Bundle Name, Order No, Part Number, Part Description, Serial Number.
  Sections are separated by a blank line and each is prefixed with a # comment header.

F-106 Filename: bundle-velocity-YYYY-MM-DD.csv.

F-107 Member WO metadata sourced from the Bundle Definition CSV. Program is inferred per-bundle from the first member WO that carries a Program value.

F-108 Lookback and exclude-current-month controls dynamically update the period info label showing the actual month range and count.

6.11 CPI Overlay (v1.4, formula revised v1.7)

Productivity charts answer "are we earning more hours over time?" but not "are we more efficient per technician-hour?". CPI = Earned Value / Actual Cost (in hours). When the VAC Tracker Log is uploaded, EHA overlays a true-aggregate CPI line on the summary and per-bundle charts so managers can read productivity and efficiency together without the planned-vs-actual distraction. (v1.4 shipped this as an earned-hours-weighted average; v1.7 switched to Σ earned / Σ actual after real-data review — see §10.)

F-120 When the VAC Tracker Log is loaded (Section 5.4), each chart that already plots earned hours is augmented with a CPI overlay line drawn against a secondary y-axis (right side). When the VAC log is absent, charts render identically to v1.3 (no overlay, no secondary axis).

F-121 Per-WO CPI lookup — carry-forward. For each work order and target month m, CPIwo,m = the CPI of the latest VAC log sample for that WO whose Date is on or before the last day of month m. If no such sample exists, the WO contributes nothing to that month's overlay. Carry-forward is correct because the VAC log's CPI is cumulative through the snapshot date.

F-122 (v1.7) Monthly aggregation — true aggregate CPI. For a set of in-scope WOs (lab-wide on the summary chart, bundle-scoped on each bundle chart), the overlay's value at month m is Σ EarnedHrswo,m ÷ Σ ActualHrswo,m, where ActualHrswo,m = EarnedHrswo,m ÷ CPIwo,m. WOs with no earned hours that month, no qualifying CPI sample, or non-positive CPI are excluded from both sums. Months with zero total actual hours render as Chart.js gaps (no point drawn). This number reconciles exactly with the Earned Hours / Actual Hours pair shown in the marker tooltip.

F-123 Dynamic recompute on chip toggle. Program filter chip changes (including Select All / Deselect All) trigger a full re-render via applyFilters(), which rebuilds the CPI overlay from the still-selected WOs in the same code path as v1.3 earned-hours recomputation. No separate Apply click is needed.

F-124 Dynamic recompute on legend toggle. When a user toggles a bundle line (summary chart) or root-part line (bundle chart) off via the chart legend, the overlay recomputes from only the still-visible datasets' contributing WOs. The CPI dataset itself is excluded from the Grand Total / Bundle Total recompute path so its values (near 1.0) never pollute the hours total.

F-125 If the loaded VAC log contains no qualifying samples for any in-scope WO at any month in the chart's range, the overlay is skipped (no secondary axis added, no orphan line drawn).

F-126 The CPI overlay dataset and its yAxisID are serialized into snapshots so a saved snapshot still renders the line and the secondary axis. Snapshot legend toggling continues to skip CPI from the total recompute. Live dynamic recompute is not re-executed in snapshots (the snapshot is a frozen view).

F-127 (v1.5) CPI data point marker: CPI data points render as 'crossRot' (X) markers rather than circles. This visually differentiates the CPI line from earned-hours bundle lines (which use circle points) and from total lines (which use dashed strokes).

6.12 Legend Click Cycle (v1.5)

The default Chart.js legend behavior is a two-state toggle (visible / hidden). When a user wants to focus on a single part number, repeatedly hiding every other line is tedious. The v1.5 cycle adds an isolation state as the second click on the same item; the third click returns the chart to its everything-on baseline.

F-128 Each part-number legend entry (root-part dataset on a bundle chart, bundle name on the summary chart) has a per-dataset cycle counter advanced by each click: 0 (visible) → 1 (hidden) → 2 (isolated — this dataset visible, all other part-number datasets hidden) → 0.

F-129 Stack hides — cross-item independence. Clicking different part-number items advances each counter independently. Two items can simultaneously be in state 1 (both hidden); only one item can be in state 2 at a time. Entering state 2 demotes any prior state-2 item to state 1 (so its hidden visibility is preserved when isolation is later released).

F-130 Global reset on 2→0 transition. The third consecutive click on an item in state 2 zeroes every part-number counter on that chart, returning the chart to its default everything-on view. Total + CPI dataset hidden states are NOT touched by the reset — they retain whatever the user set via direct legend clicks on those items.

F-131 Grand Total / Bundle Total legend clicks and CPI dataset legend clicks use the standard Chart.js visibility toggle and do NOT advance the cycle. Toggling the total line off via legend still recomputes nothing about the cycle; toggling the CPI line off hides the overlay without affecting cycle state.

F-132 Re-running Analyze, changing the start-date filter, or toggling a program chip destroys + rebuilds all chart instances, naturally resetting cycle state to 0 on every dataset.

F-133 The cycle handler is inlined into snapshot HTML so saved snapshots retain the same interactive behavior.

6.13 CPI Tooltip (v1.6 / v1.8 / v1.10)

v1.10 history note: the tooltip was originally introduced in v1.6 to show derived Earned Hours and Actual Hours alongside the CPI value, on the theory that the floor would want both halves of the ratio. The Coverage line was added in v1.8 after the silent-failure risk surfaced. v1.10 removes both the Earned and Actual lines — see §6.14 for the rationale.

F-134 (revised v1.10) When the CPI dataset is part of a tooltip's items (i.e. the user hovers a CPI X marker or, in index mode, a month with CPI data), the tooltip is augmented with ONLY the Coverage line below the CPI value. The earlier Earned Hours and Actual Hours lines have been removed.

F-135 (retired v1.10) The derived Earned/Actual sums F-135 originally defined are no longer rendered. The Earned-Hours figure was redundant with the visible bars / lines on the chart, and the derived Actual Hours value (Earned ÷ CPI) was structurally misleading because the VAC tracker's CPI is computed by Gate Tracker as Percent Complete × Baseline ÷ Total Actual Hours — not as Σ Hours Earned ÷ Σ Actual. Mixing the two pipelines produced an "Actual" that could be off from the real Peabody Total Actual Hours by 2× or more. See §6.14.

F-136 (retired v1.10) The reconciliation property described in v1.7 (CPIm = EarnedHoursm ÷ ActualHoursm by construction) was a true statement about the displayed numbers internally, but the "ActualHours" in that identity was the derived-from-CPI value, not the real measured actual. Removing the Actual line removes the source of confusion.

F-137 (revised v1.10) When the user hovers the CPI item in the chart legend, an HTML tooltip is positioned near the cursor describing the CPI line in plain language: "Each month's CPI is an earned-hours-weighted average of the per-WO CPI samples from the uploaded VAC tracker log. Each WO's CPI carries forward from the latest sample dated on or before the end of that month. WOs with no earned hours that month, or no qualifying CPI sample, are excluded." A second paragraph explains the Coverage line. A third, smaller note reminds the reader that the CPI values come from the VAC tracker as Gate Tracker computed them and that the line is most useful as a trend / change-over-time indicator rather than an absolute level. The original v1.6 wording — which spelled out Σ EarnedHrs ÷ Σ ActualHrs with the ActualHrs = EarnedHrs ÷ CPI derivation — has been retired.

F-138 (revised v1.10) The Coverage value is precomputed at snapshot save time and inlined into the snapshot HTML so the snapshot tooltip renders identically without the live WO objects + hoursMap. Earned and Actual slots are no longer written into the snapshot (they were under F-138's original wording).

F-139 (v1.8) Coverage indicator. The CPI marker tooltip shows Coverage: NN%. Computed as Σ EarnedHrswo,m over WOs that have a qualifying CPI sample ÷ Σ EarnedHrswo,m over all in-scope WOs (including those WITHOUT a qualifying CPI sample). Earned-hours-weighted; rounded to the nearest integer percent. Always shown when finite (including 100%, which reassures the read is complete). Recomputes live with the legend cycle and program chip filter; precomputed at snapshot save time and stored on chartConfigs[i].cpiTooltipData[i].coverage as an integer. Unaffected by the v1.10 removal of Earned/Actual — the Coverage value is computed purely from earned-hours sums (CPI never appears in its numerator or denominator) so it doesn't inherit any EV-formula bias.

6.14 CPI line scope clarification (v1.10)

The CPI line in EHA reflects what Gate Tracker writes into the VAC tracker log. Gate Tracker's per-WO CPI is computed as:

CPIwo = (Percent Complete × Baseline) ÷ Total Actual Hours

All three terms come straight from the P File (Peabody export). EV is therefore not the sum of Hours Earned for closed operations — it's a Peabody-field product. Real-data inspection confirmed that this EV can diverge from Σ Hours Earned (closed ops) by 2× or more on the same WO and snapshot date, depending on how the planning system computes the Percent Complete field (op-closure weight, labor progress, planner judgment, partial credit, etc.).

Consequences for EHA:

  • Earned Hours bars / lines: unchanged — they come from the Hours Earned CSV directly, no CPI involved.
  • CPI overlay line: shows whatever Gate Tracker computed. Most useful as a trend indicator (slope, change in response to operational initiatives) rather than as an absolute level.
  • Coverage indicator: still meaningful — measures completeness of the CPI-sample slice, independent of CPI level.
  • Derived "Actual Hours": removed from the tooltip in v1.10 (see F-134/F-135/F-138). Surfacing a derived number that mixed two different EV pipelines was worse than not surfacing it at all.

If the user wants a strictly "Σ Hours Earned ÷ Σ Actual" CPI line instead of Gate Tracker's Peabody-driven CPI, the VAC Tracker Backfill Tool emits exactly that, in the same CSV format EHA accepts. Uploading the backfill's output as the VAC tracker input swaps EHA's CPI line from Gate Tracker's formula to the backfill's formula without any other tool change.

6.14 Operation-Scope Filter — Oper Type = MFG (v1.9)

EHA is the primary consumer of the Hours Earned CSV across the tool suite, so EHA owns the canonical contract for the new Oper Type column. Score Card and VAC Backfill both honor the same column with parallel filter logic.

F-140 (v1.9) Optional Oper Type column in the Hours Earned CSV. aggregateHours() looks up the column via colIndex(). When present, the row loop drops every row whose value (after String().trim().toUpperCase()) is not MFG and increments a nonMfgSkipped counter. Excluded rows never enter hoursMap and therefore never appear in any chart, table, CPI tooltip, or snapshot. When the column is absent (legacy export), all rows pass through unchanged for backward compatibility, and a prominent warning is surfaced at both upload time AND in the validation panel.

F-141 (v1.9) Upload-time status. The file-input handler probes the header row for Oper Type the instant the user picks a file (before Analyze runs). Two states:

  • Column present: green/loaded status — "Loaded N data rows — Oper Type column found, MFG filter will apply on Analyze".
  • Column absent: yellow/warning status — "Loaded N data rows — WARNING: no Oper Type column, operation-scope filter INACTIVE (CPI may be biased by non-MFG earned hours)".

F-142 (v1.9) Analyze-time validation panel. Two warning lines may surface in the validation panel via the existing aggWarnings array returned by aggregateHours():

  • "N non-MFG row(s) excluded by Oper Type filter" when the column was present and rows were filtered. Informational.
  • "Operation-scope filter INACTIVE — Hours Earned CSV has no Oper Type column. Earned hours for non-manufacturing ops (QA, engineering, ...) are being included; CPI may be biased upward. Re-export with the Oper Type column to engage the filter." when the column is absent. Renders even when no other warnings exist.

F-143 (v1.9) No bypass toggle. When the Oper Type column is present, the filter is always engaged. There is no UI control to disable it. This is intentional — the bias the filter prevents is steady and invisible to per-row sanity checks, so allowing it to be turned off would re-open the failure mode it was added to close (user decision, 2026-05-19).

F-144 (v1.9) Filter happens BEFORE the date/hours parsing in the row loop, so excluded rows don't contribute to badDates or badHours counters. The aggregations on the Earned-Hour-Analysis side never see non-MFG hours; CPI, bundle totals, unbundled totals, and snapshot exports are all consistent.

10. Resolved Design Questions

  1. Regions reset on every Apply (v1.3 decision): Averaging regions are intentionally per-render. Persisting them across filter changes would create ambiguous behavior when month bounds shift (region indices reference month positions, not month keys). Kept as-is.
  2. Unbundled CSV stays in bundle-definition format (v1.3 decision): The unbundled CSV is a burndown list — work orders that should be added to a bundle. The output format matches the Bundle Definition CSV intentionally so it can be opened, edited (assign a BundleName), and re-imported. Monthly-hours columns would be informational only and aren't useful to the burndown workflow.
  3. Select All / Deselect All chips (v1.3 ADDED, F-12a): Two bold chips at the start of the program filter bar. Each click of any program chip or bulk chip immediately re-renders (no separate Apply click required for program filtering).
  4. CPI input source — VAC Tracker Log over a new Actual Hours CSV (v1.4 decision): Gate Tracker already exports the VAC log with a precomputed CPI per WO per snapshot date. Re-using that artifact avoids creating a new artifact users have to maintain. Trade-off: aggregate CPI is an earned-hours-weighted average of per-WO ratios rather than a pure ΣEV ÷ ΣAC. The two differ only when WO-level EV/AC ratios vary substantially; for the productivity-trend storytelling this tool supports, the weighted average is the more meaningful framing anyway (months that earned more hours weight more heavily in that month's efficiency reading).
  5. CPI aggregation method — weighted, not simple average (v1.4 decision, REVERSED in v1.7): v1.4 shipped an earned-hours-weighted average per-WO CPI — Σ(CPIwo × earnedwo) ÷ Σ earnedwo. v1.7 reversed this after real-data review surfaced material divergence between the weighted CPI and the true aggregate Σearned ÷ Σactual (Oscar saw weighted=0.8 vs aggregate=0.4 and weighted=1.2 vs aggregate=0.5 in consecutive months). The drag-hiding behavior was the opposite of what management framing needs. The v1.4 trade-off had been documented as a small mathematical gap; in practice it was large enough to mislead. See v1.7 decision below.
  6. Cycle cross-item behavior — stack hides (v1.5 decision): When a part-number cycle is in flight on item A (state 1 or 2) and the user clicks part-number item B, B's counter advances independently rather than resetting A. Mental model: each line has its own "hide me" toggle, plus a shared "isolate me" mode. Considered alternatives: (a) reset and start fresh on the new item; (c) replace isolation with the new item. Stack-hides preserves more user intent across multi-step interactions and only forfeits the rare case where the user wants to discard prior hides; that case is recoverable in one click on the most-recently-isolated item (3rd click triggers global reset).
  7. Actual Hours method — literal Σ(earned÷CPI) per WO (v1.6 decision, preserved in v1.7): The Actual Hours number under the CPI tooltip sums each WO's implied actual hours from its own CPI sample. v1.6 accepted a small gap between this and EarnedTotal÷CPIshown; v1.7 removed that gap by switching the displayed CPI itself to the true aggregate (which is exactly EarnedTotal ÷ this same Σactual). Earned + Actual + CPI now reconcile arithmetically.
  8. CPI aggregation switched to Σ earned ÷ Σ actual (v1.7 decision): True aggregate — drag-honest, reconciles with the displayed Earned / Actual numbers. The earlier v1.4 mathematical pre-commitment to a weighted-by-earned average was overruled by real-data review. Considered alternatives at the time of the switch: simple mean of per-WO CPI (volatile, what Gate Tracker uses on the VAC plot) and keeping the weighted formula (rejected on drag-hiding grounds). The chosen method directly answers the question this tool exists to answer: "is the lab efficient as a whole?".
  9. Coverage indicator pattern (v1.8 decision): Any aggregation that depends on sparse / optional data must surface its data completeness in the same hover affordance that shows the aggregate. v1.4 shipped CPI without one and the silent-failure risk only surfaced during Oscar's real-data review — he could have briefed management with cross-month comparisons that were materially distorted by missing VAC tracker history for the N program. The fix in v1.8 is a single tooltip line ("Coverage: NN%") showing the earned-hours-weighted fraction of in-scope hours that has a qualifying CPI sample. Generalized as a process reminder for future visualizations.
