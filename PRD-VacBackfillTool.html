Product Requirements Document (PRD)

Product Name: VAC Tracker Backfill Tool

File: vac-backfill-tool-1.html

Version 1.7 | May 19, 2026 | Author: Oscar Castillo

1. Overview

A client-side, one-shot tool to fill in missing VAC tracker history for work-order/program combinations that lack P File coverage. Reads tech-charges .xlsx exports (per-employee, per-operation, per-week-ending) plus the Hours Earned CSV, then computes weekly cumulative actual hours and cumulative earned hours per WO and emits a CSV in the exact same format Gate Tracker's exportVacLog() produces (Date, WO, Part #, VAC, CPI). Oscar merges the output into his live VAC tracker externally; no other tool in the suite changes.

An optional third input — the live VAC tracker CSV — activates a comparison panel that surfaces any work-order/date pairs where the backfill CPI diverges materially from the live VAC tracker CPI. This catches calibration issues between the two data paths before the user merges anything.

2. Objectives

  • Backfill the VAC tracker for periods where P Files are unavailable (e.g., the N program back to June 2025), so that downstream tools (Earned Hour Analysis) can show meaningful CPI history.
  • Match the exact output format of Gate Tracker's exportVacLog() so merging is a plain text concatenation, with no schema changes anywhere else.
  • Emit at weekly granularity, matching the cadence at which P Files are normally captured.
  • Provide a sanity-check comparison against the live VAC tracker so divergences are caught before they reach EHA.
  • Surface validation diagnostics for charges that have no earned credit, WOs missing from one of the inputs, and similar data anomalies.

3. Architecture Constraints

  • Entirely client-side; all parsing, computation, and CSV generation happens in the browser.
  • Single self-contained HTML file with embedded libraries (no CDN).
  • No persistent storage (no cookies, localStorage, IndexedDB).
  • Must work in modern browsers (Chrome, Edge).
  • Same security envelope as the rest of the suite: esc() XSS prevention on dynamic HTML, CSP meta tag, CSV field quoting + length cap.

5. Data Inputs

5.1 Tech Charge files (.xlsx, required, multiple)

Identical schema to PRD-EmployeeScoreCard.html §5.1. Each file's data table starts on row 4 (rows 1–3 are export metadata). The header row is auto-detected by scanning the first 10 rows for a cell whose normalized value matches Order No (case-insensitive, punctuation/whitespace tolerant via normHeader()).

Week EndingDate/TimeSnapshot date. Format MM/DD/YYYY HH:MM:SS AM/PM. Drives the output cadence.
BadgeStringEmployee identity. Used as part of the dedup key and as a sub-series key for cumulative aggregation.
OperationStringOper No. Used as a sub-series key.

Multi-file ingest: rows are concatenated across files, then deduplicated by composite key (Badge, Order No, Operation, Week Ending) keeping the row with the maximum Total Hours (most-recent-snapshot wins). Per-file try/catch: one bad file does not abort the batch; failures are recorded in the status line.

Format: exportVacLog() output — Date, WO, Part #, VAC, CPI. Only Date, WO, and CPI are read; Part # and VAC are ignored. Rows with blank or non-numeric CPI are skipped (counted in the status line).

6. Functional Requirements

6.1 Data Processing

F-01 Auto-detect the header row in each xlsx by scanning the first 10 rows for a cell whose normalized value matches Order No. Use normHeader() (case-insensitive, punctuation- and whitespace-tolerant) so headers like Order No. or Order No resolve correctly. Files without a matching header are recorded as per-file failures; the batch continues with the remaining files.

F-02 After concatenating rows from all uploaded xlsx files, deduplicate by composite key (Badge, Order No, Operation, Week Ending). When duplicates exist, retain the row with the maximum Total Hours.

F-03 (v1.1) For each work order, compute weekly cumulative actual hours under one of two modes selected by the "Charge totals format" dropdown in the action bar:

  • Incremental (default): each charge row represents that week's hours. cum_actual_W = Σ row.totalHours for all charge rows where Week Ending ≤ W. Use this for real-world weekly labor-system exports.
  • Cumulative per Badge+Op: each charge row is the running total through Week Ending for that (Badge, Operation) tuple. cum_actual_W = Σ latest Total Hours (where Week Ending ≤ W) across each (Badge, Operation) series for the WO. Use this when the export reports cumulative values (matches the Employee Score Card PRD §5.1 wording and the synthetic test fixtures).
Default is incremental because Oscar's v1.0 real-data test surfaced that the live labor-system export is incremental, contradicting the Score Card PRD's "cumulative-as-of-Week-Ending" description. The toggle exists so the synthetic fixtures (which are cumulative by design) can still be reproduced.

F-04 For each WO, compute weekly cumulative earned hours: sum Hours Earned over all rows in the Hours Earned CSV whose effective date ≤ the target week. Effective date precedence: Actual End Date column if present and parseable, otherwise last-day-of-(Year, Month). (v1.5) The v1.2 pre-charge-week lower bound was removed — the labor system returns full WO history regardless of the user's start-date filter, so the scenario the lower bound was protecting against doesn't occur in practice. See §11.10 for the decision history.

F-05 For each (WO, Week Ending) tuple where cumulative actual > 0: emit one output row. CPI = cumulative_earned / cumulative_actual rounded to 3 decimal places, or blank when cumulative_earned == 0 (mid-WO read with no closures yet). (v1.6) Per-WO emission cutoff: within the per-WO loop, emit rows through the FIRST global Week Ending W where Wts ≥ woFreezeTs, where woFreezeTs = max(latest charge Week Ending for the WO, latest Hours-Earned effective date for the WO). After that point the cumulative values stop changing, so additional rows would be identical duplicates — they're not emitted. Matches how Gate Tracker behaves: a WO appears in weekly P-File runs while it's active, then stops appearing once it closes. (v1.2 / revised v1.4) CPI sanity threshold: if the raw computed CPI exceeds the user-configurable sanity threshold (default 3.0), the row is marked flagged for diagnostics and visually highlighted in the preview table (amber tint + warning marker). (v1.4) The raw CPI value is still written to the downloaded CSV — high CPI is often legitimate (e.g. a planner releasing large block hours when an op closes) rather than a coverage gap, so blanking it was over-aggressive. Triage happens via the "Flagged WOs" report (§6.4) and the comparison-against-live-VAC-tracker panel (§6.5).

F-06 Output rows are sorted by Date ascending, then WO ascending. Matches the ordering produced by Gate Tracker's exportVacLog() so a downstream re-sort is not required after merge.

F-07 Date values are formatted as M/D/YYYY (no leading zeros). VAC column is always blank in the output; Gate Tracker recomputes it on its next P File run.

6.2 Validation

F-10 Collapsed validation panel surfaces (each section appears only when non-empty):

  • Per-file parse errors from xlsx ingest (missing header, missing required columns, etc.).
  • WOs with charges but no Hours Earned — emitted with blank CPI throughout; flagged for follow-up.
  • WOs in Hours Earned but no charges — no backfill row emitted; flagged so the user knows the gap exists.
  • (WO, Week Ending) pairs with charges but cumulative earned still zero — mid-WO snapshots before any operation closed. Listed for spot-check; rows still emitted with blank CPI.
  • (v1.2) WOs with Hours Earned entries predating their first charge week — row count + total earned hours excluded per WO. Reports F-04's lower-bound exclusion so users can see where coverage gaps are causing data loss.
  • (v1.2) Rows with CPI above the sanity threshold — sample of WO/date/raw-CPI/earned/actual for the first 15. Most actionable item: surfaces the WOs whose work probably happened before the charge data start so the user can decide whether to (a) raise the threshold if the data is in fact correct, or (b) trust the blank CPI and merge accordingly.

6.3 Output

F-20 Preview table displays all computed rows: Date, WO, Part #, Cumulative Earned, Cumulative Actual, CPI. Cumulative columns are displayed for transparency but excluded from the downloaded CSV. Blank CPI rendered as the muted text "blank".

F-21 "Download Backfill CSV" button writes the exportVacLog-format CSV (Date, WO, Part #, VAC, CPI header + rows). Filename: vac-backfill-YYYY-MM-DD.csv. CSV cell escape follows the Score Card S-06 pattern: 32K-byte cap per cell + double-quote escape on commas/quotes/newlines.

6.4 Comparison vs Existing VAC Log (optional)

Activates only when the user uploads the optional VAC Tracker Log CSV in input slot 3.

F-30 For each row in the existing VAC log, find the closest-by-date backfill row for the same WO within a tolerance window. Default: ±7 days. User can adjust the tolerance via a number input at the top of the comparison panel.

F-31 Compute Δ CPI = backfill_CPI − existing_CPI. Tag the pair as a "wild inconsistency" when |Δ| ≥ threshold. Default threshold: 0.10. User can adjust via a number input.

F-32 Comparison panel surfaces:

  • Summary stats: overlapping rows, flagged count, max |Δ|, mean Δ, median Δ, unmatched-existing count.
  • Top-20 table sorted by |Δ| descending: WO, existing date, existing CPI, matched backfill date, backfill CPI, Δ. Flagged rows highlighted amber.
  • WOs only in backfill output (collapsible list).
  • WOs only in existing VAC log (collapsible list).
  • Existing rows with no backfill match within tolerance (collapsible list, first 100 shown).

F-33 "Recompute" button next to the threshold + tolerance inputs reruns the comparison without reprocessing the input files.

F-34 "Download Comparison CSV" writes a multi-section CSV: header rows naming the active threshold/tolerance, then four sections separated by blank lines + # comment headers: overlap pairs (with Flagged column), unmatched-existing rows, only-in-backfill WOs, only-in-existing WOs. Filename: vac-backfill-comparison-YYYY-MM-DD.csv.

F-35 (v1.7) Per-Part-# comparison plots. Below the existing comparison panel, render one canvas plot per Part # (sorted ascending), each plotting CPI over time for every WO of that Part #. Each WO gets a stable color from a 10-hue palette. Backfill series: solid 1.5px line + filled circles (3.5px radius). Existing VAC log series: dashed 1.5px line + filled diamonds (4.5px half-diagonal), same color as the WO's backfill series. Reference line at CPI = 1.0 (dashed gray). Y-axis 0 to max(1.2, maxCPI × 1.1), uncapped if any CPI exceeds 5. X-axis 5 evenly spaced date ticks across the union of backfill + existing date ranges for that Part #. Per-plot legend below the canvas lists each WO with its color swatch and a marker hint ("solid + dashed" / "solid only" / "dashed only"). Hover within 14px of any plotted point surfaces a tooltip showing WO, source (backfill or existing), date, and CPI. Plot data structure groups by Part # from the backfill rows' partNo field, falling back to a backfill-derived WO→Part# lookup for any existing-VAC row whose Part # column is missing or whose WO has no backfill rows. See §11.12.

11. Design Decisions & Notes

11.1 Library splicing — raw bytes only

The SheetJS minified code contains a U+0085 (NEL) byte sequence inside a Unicode-character lookup table. Python's str.splitlines() treats U+0085 as a line break and drops it on rejoin, corrupting the lookup table. When extracting the SheetJS / PapaParse blocks from the Score Card source, use bytes operations only (find + slice on b'</script>' markers). Verified during v1.0 build — the bug manifested as typeof XLSX === 'undefined' at runtime even though the script tag was present.

11.2 Weekly granularity (decision, v1.0)

Output emits one row per (WO, Week Ending) from the WO's first charge week forward. Chosen over monthly bucketing because:

  • P Files are typically captured weekly; the backfill should look like a real weekly P File run.
  • Higher resolution gives EHA more flexibility for downstream displays.
  • The marginal cost in output size (~6× vs. monthly) is trivial for a one-shot CSV.

11.3 WO-level cumulative actual (decision, v1.0)

Cumulative actual aggregates across all operations of a WO, including those that have not yet earned credit. This matches Gate Tracker's Total Actual Hours semantics from the P File. A consequence is that a WO with one closed operation and one ongoing operation reports a CPI that already reflects the ongoing op's hours — identical to what Gate Tracker would show. Operation-level CPI would be a different feature and is out of scope for v1.0.

11.4 VAC column blank in output (decision, v1.0)

Computing VAC requires baseline hours per WO, which is not present in either input. Leaving VAC blank is correct — Gate Tracker's exportVacLog() already merges by (Date, WO) on its next run, so VAC will be re-populated automatically once a real P File becomes available for the period.

11.5 Comparison threshold and tolerance defaults (decision, v1.0)

Default |Δ| threshold of 0.10 chosen to flag ≥ 10-percentage-point CPI deltas (a substantive operational mismatch worth investigating, not normal rounding noise). Default date tolerance of ±7 days handles cases where the two systems sample at slightly different weekday cadences. Both are user-adjustable in the panel.

11.11 Per-WO emission cutoff at woFreezeTs (v1.6)

v1.5 still emitted a row for every WO at every global Week Ending from the WO's first charge week onward, even for weeks long past the WO's last activity. Real-data symptom: a WO that closed in July 2025 had ~40 rows in the backfill stretching through April 2026, all carrying identical cum_earned and cum_actual values (the WO's frozen state). Oscar caught this asking "should a WO completed in July 2025 still be reporting CPI in 2026?"

The right answer is no — once a WO has no new charges and no new earned, its CPI is a historical record, not a current reading. Continuing to emit the same numbers week after week:

  • Inflates CSV size with no informational value.
  • Adds noise to the comparison panel as "only in backfill" rows (the live VAC tracker stops emitting once Gate Tracker stops seeing the WO in its P-File runs — we should match that behavior).
  • Confuses anyone reading the merged VAC tracker manually ("why is this WO repeated weekly long past close?").

v1.6 adds the cutoff inside the per-WO loop. For each WO we compute woFreezeTs = max(latest charge weekTs, latest earned effTs) and emit rows through the FIRST global Week Ending whose timestamp is at or after that freeze date. Beyond that point, the inner loop breaks.

Verified on the Score Card fixtures: total emitted rows dropped 20 → 9 (55% reduction), all CPI values unchanged (WO-100 = 1.091, WO-400 = 1.250, WO-500 = 0.833, WO-600 = 1.000, WO-200 = 0.800). The cutoff only removes redundant frozen-state duplicates, never meaningful data.

Note: EHA's monthly CPI line was never affected by the over-emission because EHA gates its per-WO contribution on "earned hours > 0 in the target month" (a closed WO has no in-month earned). The v1.6 fix is hygiene for the VAC tracker file and for the comparison panel, not a correctness fix for the EHA chart.

11.12 Per-Part-# comparison plots (v1.7)

Numeric stats in the existing comparison panel (mean/median Δ, top-20 table) summarize divergence but flatten the time dimension — Oscar couldn't tell whether the disagreement was steady, growing, or concentrated in one calendar window. He asked for plots: "very similar to what you already do in the gate tracker, plot over time and give me a mouse over at each data point with the cpi value. I want to see the deviation between the two approaches."

Design choices, all confirmed with the user:

  • Grouping unit = Part # (not root part, not all-in-one). Each canvas covers a single Part #, so the visual density of one chart is always proportional to that part's WO count. Root-grouping could be a future toggle if the data justifies it.
  • Per-WO double line (not per-source aggregate). A WO's backfill series and existing series share a color so the eye can pair them. Solid + circles for backfill, dashed + diamonds for existing — consistent with chart conventions where solid carries the "primary" series (the new computed values) and dashed carries the reference (the live tracker).
  • Position: below the existing comparison panel. The numeric stats answer "is there a problem?" at a glance; the plots answer "where and when?" once the user wants to dig in.

Implementation notes:

  • Self-contained 2D canvas rendering — no external chart library. Chart.js was rejected because the existing tool has no chart dependency and the comparison plot needs a custom point hit-test (nearest-point across two interleaved series per WO) that doesn't map cleanly onto Chart.js's tooltip plugin.
  • Hover hit-radius = 14 canvas-units. Tooltip is absolutely positioned inside the plot wrap and auto-flips to the left side when too close to the right edge.
  • Existing VAC log gained a Part # column read in v1.7 (the existing parser ignored it through v1.6). When a VAC row has no Part #, the renderer looks up the WO in a backfill-derived map first — this prevents an "(no part #)" bucket from collecting WOs that already have a confirmed Part # from the charge files.
  • Y-axis cap: max(1.2, maxCPI × 1.1), but uncapped when any CPI exceeds 5 so high-CPI flagged rows still plot inside the frame. CPI = 1.0 dashed gray reference line is always drawn so the operationally interesting threshold is visible at a glance.

11.10 F-04 per-WO earned filter removed (v1.5)

v1.2 added a per-WO lower bound on Hours Earned: any row whose effective date was before the WO's first charge week was excluded from cum_earned. The stated purpose: prevent CPI inflation for WOs whose work happened before the user's tech-charges start window.

v1.4 real-data review surfaced two findings that combined to make F-04 actively harmful:

  1. The labor system returns full WO history regardless of the user's start-date request. The scenario F-04 was protecting against doesn't actually occur — charge data covers the WO's full lifetime even when the user pulls "from 1/1/25".
  2. F-04 was systematically biasing backfill CPI below the live VAC tracker's CPI. Example: a WO with 114.5 earned across ops closing 6/18/25 – 7/18/25 and one charge row on 6/27/25 (4 actual hours). Gate Tracker computed CPI = 25.4 (114.5 / ~4.5). Backfill computed CPI = 2.25 because F-04 discarded the 105.5 earned hours that closed before 6/27/25, leaving only the ~9 hours of post-6/27 closures ÷ 4 actual. The two numbers can no longer be compared apples-to-apples, defeating the comparison panel's purpose.

v1.5 removes F-04 entirely. cum_earned now sums every Hours Earned row for the WO with effDate ≤ W, no lower bound. preChargeEarnedExcluded diagnostic, validation-panel section, and the two CSV columns ("Pre-Charge Earned Rows", "Pre-Charge Earned Hours Excluded") are all removed. F-05 sanity threshold remains — legitimate high-CPI rows still surface in the Flagged WOs report for triage, but the value is no longer manipulated.

Side note from the same real-data session: Oscar identified a separate, broader issue at the data source — the Hours Earned CSV includes ALL operations (manufacturing, quality, engineering, …) while the tech-charges export is manufacturing-only. This scope mismatch systematically inflates CPI across many WOs and is not something the tool can fix on its own. v1.5 adds a permanent "operation scope alignment" tip to the tool's description so the trap is visible upfront. Once Oscar gets a manufacturing-only earned export, the comparison panel becomes truly useful.

11.9 Flagged WOs report — reframing + wording polish (v1.4)

v1.3 named this section "Coverage gap candidates" with a prescriptive intro telling the user to pull data back to the earliest earned date. v1.4 reframes it after real-data review showed the labor system actually returns the full WO history regardless of the user's start-date filter. With full charges in scope, a high earned-vs-actual ratio is more often a legitimate signal (e.g. a planner releasing 414+414 hours when two ops close the same day) than a coverage gap. The new framing is neutral about cause.

v1.4 wording changes:

  • Section header: "Coverage gap candidates" → "Flagged WOs — high earned-vs-actual ratio".
  • Intro paragraph rewritten to enumerate the three common causes (legitimate high CPI, real coverage gap, data quirk) rather than recommending a single action.
  • Per-Part # rollup column "Total earned at risk" → "Σ cum_earned (flagged WOs)". Underlying meaning fix: the value is now the sum of each flagged WO's LATEST (highest-date) cum_earned in the backfill output, not the peak-CPI snapshot.
  • Date column "Earliest charge week" (both rollup + per-WO detail) → "Earliest actuals date".
  • Validation-panel sample lines: "earned X / actual Y" → "cum_earned X / cum_actual Y".
  • Download button: "Download Gap Report CSV" → "Download Flagged WOs CSV". Filename: vac-backfill-gap-report-YYYY-MM-DD.csv → vac-backfill-flagged-wos-YYYY-MM-DD.csv.

F-70 / F-71 spec the section structure (rollup + per-WO detail) and remain accurate after the rename. The candidate set is unchanged: any WO with at least one sanity-flagged row OR any Hours Earned rows excluded by F-04. Section is hidden when the candidate set is empty.

11.8 Coverage gap report (v1.3, superseded by §11.9)

v1.2 made the data-asymmetry symptoms safe to display (blank CPI, flagged rows). v1.3 made the symptoms actionable by surfacing a per-Part # rollup of the work orders that need an earlier data pull, plus a per-WO detail table and a CSV download. The user's mental model was "I pull tech-charges data by part number," so the report was grouped by Part # with the suggested pull-back-to date (the earliest earned date across all candidate WOs of that part). The section was reframed in v1.4 (see §11.9) after real-data testing showed the "pull more data" framing was over-aggressive.

The candidate set = any WO that hit the sanity threshold (cum_earned vs cum_actual ratio too high) OR had any Hours Earned rows excluded by F-04 (effective date before the WO's first charge week). Rendering is hidden when the candidate set is empty.

F-70 / F-71 spec this section. Output CSV filename: vac-backfill-gap-report-YYYY-MM-DD.csv (renamed in v1.4 — see §11.9).

F-70 — Per-Part # rollup table columns: Part #, # WOs flagged, Earliest earned date (across the part's candidate WOs), Latest earned date, Earliest charge week (across the part's candidate WOs), Total earned at risk (sum of latest cum_earned across the part's candidate WOs). Sort by Part # ascending.

F-71 — Per-WO detail table (collapsible, defaulting closed): one row per candidate WO with Part #, WO, Earliest earned date, Earliest charge week, Latest cum_earned, Latest cum_actual, Max raw CPI (uncapped, useful even when CPI was blanked in the output), Notes (flagged row count + pre-charge excluded summary). Sort by Part # ascending, then by max raw CPI descending.

11.7 Coverage-asymmetry handling (decision, v1.2)

v1.1 surfaced inflated CPI values (25–30) in Oscar's comparison panel against the live VAC tracker. Root cause: Hours Earned has full historical context (going back to whenever the EHA pipeline started recording closures), but tech charges only start at the cutoff the user selected when exporting. For any WO whose work mostly happened before that cutoff, the tool sees full earned but only a sliver of actuals — CPI inflates by 5× or more.

v1.2 ships two complementary fixes:

  1. Per-WO earned filter (F-04, v1.2). For each WO, exclude any Hours Earned row whose effective date is before that WO's first charge week. Cleanly handles WOs that closed entirely pre-cutoff: cum_earned = 0 → CPI blank → row drops out of the comparison.
  2. CPI sanity threshold (F-05, v1.2). Catches WOs the per-WO filter can't — those whose operations closed within the charge data window but whose work happened before it. The close date is post-cutoff (so F-04 keeps the earned hours), but the actual hours are still a tiny fragment of the real work. Default threshold 3.0; raw CPI above this is set to BLANK in the output, with the row marked flagged in diagnostics. Threshold is user-adjustable from the UI without re-uploading.

Blank CPI in the output is the honest signal — downstream EHA's v1.8 coverage indicator naturally treats it as "no qualifying sample" and surfaces lower coverage % for the affected months, rather than ingesting a misleading number.

11.6 Charge totals format toggle (decision, v1.1)

v1.0 shipped with the cumulative-per-(Badge, Op) interpretation hard-coded, mirroring the Score Card PRD §5.1 wording. When Oscar tested v1.0 against the real labor-system export, backfill CPI values came back at 26–27 across many WOs while the live VAC tracker reported 5–11 for the same WOs — both implausibly high for real CPI, with the backfill consistently ~5× the live tracker. Diagnostic: the live export uses incremental Total Hours per row, not cumulative. The v1.0 algorithm's "latest Total Hours per (Badge, Op)" lookup therefore picked only the most recent week and threw away all earlier weeks, undercounting cum_actual by 4–5× and inflating CPI by the same factor.

v1.1 added a UI toggle defaulting to incremental, which sums all charge rows where Week Ending ≤ W. The cumulative mode is preserved for backwards compatibility with the synthetic Score Card test fixtures (verified: 20 rows, WO-100@3/7 still gives 60/55 = 1.091, WO-400@3/21 still gives 25/20 = 1.250). Under incremental mode the same fixtures give 20 rows with different cum_actual values (e.g., WO-400@3/21 = 5+12+20 = 37, CPI 0.676), reflecting the difference in interpretation.

This decision also exposes a latent issue in the Employee Score Card tool, which performs its own cumulative-to-incremental conversion via successive differences (Score Card F-03) under the assumption that Total Hours is cumulative. If the live export is in fact incremental, Score Card's per-employee actual-hours totals would be similarly undercounted. Out of scope for this tool but worth investigating in a follow-up.

12. Out of Scope

  • Merging the backfill into the live VAC tracker. The user concatenates externally (or future EHA could accept multiple VAC log files).
  • Computing VAC. See §11.4.
  • Operation-level CPI output. See §11.3.
  • Trending visuals. This tool emits CSV only; visualization happens downstream in EHA after the merge.
