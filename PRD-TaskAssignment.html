1. Purpose & Background

The Task Assignment Builder lets a production manager (1) build out the structure of the shop's teams — Location → Team → Team Member — and (2) assign work orders to a team, tagging the specific members responsible for each. It is the organizational/assignment layer that sits on top of the data the rest of the work-gates1 family already computes.

Crucially, the tool performs no engineering computation and requires no manual entry of work-order data. Every live field (current gate, hours, % complete, operations, planned finish) is sourced from a single CSV exported by PDVF (the Production Dependency & Velocity Forecaster, §5.8). PDVF is already scoped to the curated subset of critical hardware the manager monitors, so the assignment tool shows a short, relevant work-order list rather than every released WO. The only things the manager enters by hand are the team structure and the assignment decisions.

Single source of truth. PDVF owns the heavy computation (decoder-ring gate mapping, ETC, hours-based % complete, operation status, milestone dates). The assignment tool joins that feed by WO# and never recomputes it — eliminating the risk of two tools drifting apart.

3. Data Inputs

3.1 WO Assignment Feed (required) — from PDVF §5.8

A single CSV with a Record column distinguishing WO summary rows from OP detail rows. Joined to the plan by WO #.

RecordColumns used
WOWO, Part Number, Part Name, Program, Current Gate, Ops Remaining In Gate, Planned Hours Remaining In Gate, Planned Hours In Gate, Remaining Planned Hours (ETC), Percent Complete, Planned Finish, Active DR Ops, As Of, Serial, Avg Weekly Hours, Required Weekly Hours, Gates Remaining
OPWO, Operation No, Operation Name, Operation Gate, Operation Planned Hours, Operation Status (Active / In Queue), Is DR

New WO columns (PDVF v1.17, §5.8). Serial = the unit S/N (shown on the artifact header). Avg Weekly Hours = the WO’s actual trailing weekly velocity (h/wk) from PDVF’s EHA history — blank when no earned-hour history exists, so “no pace data” is distinct from a genuine zero. Required Weekly Hours = the pace needed to hit the milestone (h/wk, past-due aware). Gates Remaining = a packed <gate>=<hrs> list (pipe-joined) of every downstream gate with open hours, used to draw the artifact’s “Gates Remaining” bar. The task tool never recomputes these — it consumes them.

3.2 Saved Plan CSV (optional) — this tool's own export

Re-imported to restore a previously built plan. See §5 for the round-trip schema.

4. Functional Requirements

IDRequirement
F-01EXPLICIT Build a 3-level hierarchy: add / rename / delete Locations, Teams (within a location), and Team Members (within a team). Deleting a team or location returns its work orders to the Unassigned pool; deleting a member untags it everywhere.
F-01aRESOLVED Hierarchy editing is fully inline: adding a Location/Team creates an editable name field in place (no popup); names are edited by typing in that field; deletes use a two-click inline confirm (Delete → Confirm delete / Cancel). This replaced an initial prompt()/confirm() approach, which is blocked in sandboxed preview iframes (and is poorer UX).
F-02EXPLICIT Load the PDVF WO Assignment Feed; unassigned work orders appear in an Unassigned Work Orders pool.
F-03RESOLVED (v1.2) Click a work order (its title, from the pool or a team card) to open a team picker listing every Location: Team; click a team to assign, click again (✓) to unassign. Clicking the backdrop cancels. This replaced drag-drop, which failed once the team list scrolled beyond the viewport. An assigned card also has a Remove from this team button. The Unassigned pool remains as the reference list of WOs on no team.
F-04EXPLICIT Within an assigned WO (per team), tag one or more of that team's members as responsible (toggle chips). Tags are stored per (WO, team) assignment; tagging is restricted to members of that team.
F-05EXPLICIT Global view toggle between Gate Name view (default; current gate, ETC, planned finish, % complete) and Operation view.
F-06EXPLICIT Operation view lists, per WO, only the Active + In Queue operations — columns Op # / Operation / Gate / Status / Planned hrs — sorted by Op # ascending, with 7000-series (DR) operations pulled to the front and flagged. Fully explicit text (no hover tooltips), suitable for a wall monitor or printout; a Print button and print CSS are provided. The Remaining Planned Hours / Planned Finish Date / % Complete summary line is retained in Operation view too (only the redundant current-gate line is dropped). On an assigned card, each op row has a selection checkbox (this week's work); printing shows only the selected ops (unselected rows and the checkbox column are hidden; a card with nothing selected prints no table). Pool cards show the op table read-only.
F-07EXPLICIT Planned Finish per WO is the PDVF Milestone Date carried in the feed (no manual entry).
F-08EXPLICIT % Complete is PDVF's hours-based figure, refreshed on every feed load (always current; no sticky/last-known mechanism, because PDVF has no weekly P-File dependency).
F-09EXPLICIT Refresh: re-uploading a fresh feed re-joins by WO# and updates live fields + operations only — the team/member hierarchy and every assignment/tag are preserved. New WOs land in the Unassigned pool.
F-10ASSUMED A WO present in the plan but absent from the latest feed is flagged stale (amber), not deleted — so a completed/removed WO never silently disappears with its assignment history.
F-11EXPLICIT Export Plan CSV round-trips the full state (hierarchy + every WO placement + tagged members). Import Saved Plan restores it exactly.
F-12EXPLICIT Save for Editing writes a self-contained editable HTML snapshot that reopens with all state (including the active view) restored; re-uploading a feed into the snapshot refreshes live data.
F-13ASSUMED Each WO card shows an Active DR Ops badge when > 0, and stale WOs render with an amber treatment.
F-14EXPLICIT A filter box narrows the Unassigned pool by case-insensitive substring across WO # / part name / part number; the pool header shows “X of Y” while filtering, and a no-match hint when empty. Scoped to the pool only — assigned WOs under teams are unaffected. Transient (not persisted in the plan/snapshot).
F-15EXPLICIT Printing hides the Unassigned pool (@media print #pool-pane{display:none}) — a printout is the assignment board, not the intake list. (Any active filter is reflected on screen but does not affect the assigned-board printout.)
F-16EXPLICIT Multi-team work orders. The same WO can be assigned to several teams (any location) that split its operations. Each op can be selected by at most one team: an op selected by team A appears in team B's list but is disabled and labeled with the owning team. A card shared across teams shows a “shared · N teams” badge.
F-17EXPLICIT WO-card labels use technician-friendly wording: “Remaining Planned Hours” (was “ETC”) and “Planned Finish Date” (was “Finish”).
F-19RESOLVED (v1.4) Operations are feed-sourced and independent of the plan. Bug: operations are transient (only in the WO Assignment Feed, never in the Plan CSV), and importing a saved plan rebuilt every WO with empty ops — so loading the feed and then importing a plan blanked all operations (“No active / in-queue operations” on every WO). Fix: operations live in a dedicated feedOps map (keyed by WO#) written only by the feed loader and never reset by plan import; it also rides in the snapshot. Result: operations show regardless of load order. A WO not present in the loaded feed shows an actionable “upload the current WO Assignment Feed” message. Operation view also gains an “Include” checkbox column + caption clarifying that selection only curates the printout/signage — the leader always sees every operation.
F-18EXPLICIT Collapse / expand caret on every Location and Team header, with Expand all / Collapse all in the action bar. Each team header shows a work-order counter (a WO shared by two teams counts 1 for each); each location header shows a team count. Collapse state is transient (never saved): on every load / import / snapshot-open the default is all locations expanded, all teams collapsed (a newly-added team opens expanded for setup). Printing ignores collapse — it forces everything expanded, in Operation view, showing only selected ops (via printBoard()).
F-20EXPLICIT Per-team weekly goal. Once a team has work, the author can type a free-text weekly goal for that team. It is stamped with the date it was set and flagged amber “may be stale” when older than 7 days — so an out-of-date goal is visible rather than silently perpetuated. The goal survives both the snapshot and the Plan CSV (new Goal / Goal Date columns on TEAM rows). It appears on the printout and the PNG artifact.
F-21EXPLICIT The team picker now labels each team “Location · Team” (not just the team name), so an author assigning to an ambiguously-named team always sees which location it belongs to.
F-22EXPLICIT Pool view decoupled from the global toggle. The Gate/Operation toggle now only re-renders assigned cards; Unassigned pool cards stay compact and expand their operations individually via a per-card “Show operations / Hide operations” link (transient poolExpanded state). This stops the pool from ballooning when the board is switched to Operation view.
F-23EXPLICIT The location header shows the total distinct work orders assigned anywhere in that location (a WO shared by two teams in the location counts once), alongside the existing team count — e.g. “2 teams · 5 WOs”.
F-24EXPLICIT On-time pace indicator. Each WO card shows the required weekly hours to finish on time vs the WO’s actual weekly pace, colored by projected lateness: green when within +/-1 week (or ahead / complete), yellow when 1–2 weeks late, red when >2 weeks late. weeksLate = etc × (1/pace − 1/required); shown grey (“no pace data”) when the WO has no velocity history, or “no finish-date pace” when there is no milestone. Both inputs come from the PDVF feed (F-24 columns), so the tool never recomputes them.
F-25EXPLICIT Per-team PNG artifact export. Export Team PNGs generates one 1920×1080 PNG per team that has at least one assigned WO (pure canvas, modeled on Gate Tracker’s Digital Signage), auto-paginating to -p2, -p3… when a team’s blocks overflow a page; empty teams are skipped. Each sheet shows the team header, its weekly goal + set-date, and per assigned WO: Part Number, SN, Part Name (WO#) – Program; technicians assigned; Remaining Planned Hours / Planned Finish / % Complete; the selected operations only (Op # / Operation / Gate / Status / Planned Hours); a Gates Remaining bar; and the line “Close an average of X hrs/week to complete work order by <finish>”. A temporary “Preview artifact (HTML)” button renders the same layout for all teams in a new tab for format tuning (removed before final ship). Gates Remaining (v1.6): the proportional bar keeps its shape but each segment now carries only a circled number (with a per-segment minimum width so a tiny-hours gate stays a visible band); a legend beneath spells every gate out in order (“① Assembly – 50 h · ② Test – 25 h…”), so small gates are never truncated illegibly.
F-26EXPLICIT Feed is the authoritative source of live WO status, independent of upload order. The plan CSV persists the live MES fields (Current Gate, Planned Finish, Remaining Planned Hours, Percent Complete, Active DR Ops, Avg Weekly Hours, Required Weekly Hours, As Of, Serial, Gates Remaining) only as a last-known fallback; the authoring layer (hierarchy, assignments, tags, selected ops, team goal) is what the plan truly owns. The tool retains the most recent feed and re-applies it after any plan import, so importing an older plan can never overwrite fresh feed data with stale numbers (the bug where an older plan blanked the pace fields). A WO not present in the current feed — or when no feed is loaded — keeps its last-known values but shows an amber “⏳ last known · as of <date> — upload current feed” badge so stale status is never mistaken for live. Refines F-09/F-11: import restores your decisions; the feed owns live status. The retained feed rides in the snapshot; the per-WO fromFeed flag is derived, not written to the plan CSV.

5. Data Model & Round-trip Schema

Entities use stable IDs (L#, T#, M#) so the plan CSV round-trips deterministically. Work orders are keyed by WO #.

  • Location { id, name, order }
  • Team { id, locId, name, order, goal, goalDate } — weekly goal + the date it was set.
  • Member { id, teamId, name, badge (optional), order }
  • Work Order { woNo, partNo, partName, program, currentGate, etc, percentComplete, plannedFinish, activeDrOps, asOf, serial, avgWeeklyHours, requiredWeeklyHours, gatesRemaining (packed), ops[] (live, from feed), stale } — no team/tags on the WO itself.
  • Assignment (the WO↔team link, keyed teamId|woNo) { teamId, woNo, selectedOps[] (operation numbers), taggedMembers[] } — a WO can have many; operations are exclusive across a WO's assignments.

Plan CSV (one file, Type column): Type, Node ID, Parent ID, Order, Name, Badge, WO, Part Number, Part Name, Program, Current Gate, Planned Finish, Remaining Planned Hours, Percent Complete, As Of, Active DR Ops, Team ID, Tagged Member IDs, Selected Ops, Stale, Goal, Goal Date, Serial, Avg Weekly Hours, Required Weekly Hours. TEAM rows carry Goal/Goal Date; WO rows carry Serial/Avg Weekly Hours/Required Weekly Hours (the packed Gates Remaining is feed/snapshot-only, re-derived on the next feed load, not persisted to CSV — like per-operation detail). Type ∈ {LOC, TEAM, MEMBER, WO, ASSIGN}. WO rows carry the live fields + Stale; ASSIGN rows carry Team ID, pipe-joined Tagged Member IDs and Selected Ops (operation numbers). Per-operation detail (names/hours) is not persisted — it is transient/live and re-derived from the next feed load; only the operation numbers a team selected are stored. Import accepts the legacy v1.1 layout (single Team ID on the WO row) and converts it to one assignment.

7. Glossary

  • WO Assignment Feed — the PDVF §5.8 export consumed as this tool's primary input.
  • DR operation — a discrepancy/non-conformance operation, detected by operation number in the 7000–7999 range; surfaced first in Operation view.
  • Stale WO — a work order still in the plan but no longer present in the latest feed.
  • Hours-based % complete — 1 − remaining ÷ planned hours, computed by PDVF; blank when no decoder-ring labor total exists.
