1. Purpose & Background

The Task Assignment Builder lets a production manager (1) build out the structure of the shop's teams — Location → Team → Team Member — and (2) assign work orders to a team, tagging the specific members responsible for each. It is the organizational/assignment layer that sits on top of the data the rest of the work-gates1 family already computes.

Crucially, the tool performs no engineering computation and requires no manual entry of work-order data. Every live field (current gate, hours, % complete, operations, planned finish) is sourced from a single CSV exported by PDVF (the Production Dependency & Velocity Forecaster, §5.8). PDVF is already scoped to the curated subset of critical hardware the manager monitors, so the assignment tool shows a short, relevant work-order list rather than every released WO. The only things the manager enters by hand are the team structure and the assignment decisions.

Single source of truth. PDVF owns the heavy computation (decoder-ring gate mapping, ETC, hours-based % complete, operation status, milestone dates). The assignment tool joins that feed by WO# and never recomputes it — eliminating the risk of two tools drifting apart.

A single CSV with a Record column distinguishing WO summary rows from OP detail rows. Joined to the plan by WO #.

RecordColumns used
WOWO, Part Number, Part Name, Program, Current Gate, Ops Remaining In Gate, Planned Hours Remaining In Gate, Planned Hours In Gate, Remaining Planned Hours (ETC), Percent Complete, Planned Finish, Active DR Ops, As Of
OPWO, Operation No, Operation Name, Operation Gate, Operation Planned Hours, Operation Status (Active / In Queue), Is DR

3.2 Saved Plan CSV (optional) — this tool's own export

Re-imported to restore a previously built plan. See §5 for the round-trip schema.

4. Functional Requirements

IDRequirement
F-01EXPLICIT Build a 3-level hierarchy: add / rename / delete Locations, Teams (within a location), and Team Members (within a team). Deleting a team or location returns its work orders to the Unassigned pool; deleting a member untags it everywhere.
F-01aRESOLVED Hierarchy editing is fully inline: adding a Location/Team creates an editable name field in place (no popup); names are edited by typing in that field; deletes use a two-click inline confirm (Delete → Confirm delete / Cancel). This replaced an initial prompt()/confirm() approach, which is blocked in sandboxed preview iframes (and is poorer UX).
F-02EXPLICIT Load the PDVF WO Assignment Feed; unassigned work orders appear in an Unassigned Work Orders pool.
F-03EXPLICIT Drag a work order onto a team to assign it. A WO lives under exactly one team at a time but can be moved between teams (drag again) or back to the pool. Moving a WO to a different team clears its tagged members (members belong to a specific team).
F-04EXPLICIT Within an assigned WO, tag one or more of that team's members as responsible (toggle chips). Tagging is restricted to members of the WO's own team.
F-05EXPLICIT Global view toggle between Gate Name view (default; current gate, ETC, planned finish, % complete) and Operation view.
F-06EXPLICIT Operation view lists, per WO, only the Active + In Queue operations — columns Op # / Operation / Gate / Status / Planned hrs — sorted by Op # ascending, with 7000-series (DR) operations pulled to the front and flagged. Fully explicit text (no hover tooltips), suitable for a wall monitor or printout; a Print button and print CSS are provided. The ETC / Planned Finish / % Complete summary line is retained in Operation view as well (only the redundant current-gate summary line is dropped, since the per-op Gate column covers it).
F-07EXPLICIT Planned Finish per WO is the PDVF Milestone Date carried in the feed (no manual entry).
F-08EXPLICIT % Complete is PDVF's hours-based figure, refreshed on every feed load (always current; no sticky/last-known mechanism, because PDVF has no weekly P-File dependency).
F-09EXPLICIT Refresh: re-uploading a fresh feed re-joins by WO# and updates live fields + operations only — the team/member hierarchy and every assignment/tag are preserved. New WOs land in the Unassigned pool.
F-10ASSUMED A WO present in the plan but absent from the latest feed is flagged stale (amber), not deleted — so a completed/removed WO never silently disappears with its assignment history.
F-11EXPLICIT Export Plan CSV round-trips the full state (hierarchy + every WO placement + tagged members). Import Saved Plan restores it exactly.
F-12EXPLICIT Save for Editing writes a self-contained editable HTML snapshot that reopens with all state (including the active view) restored; re-uploading a feed into the snapshot refreshes live data.
F-13ASSUMED Each WO card shows an Active DR Ops badge when > 0, and stale WOs render with an amber treatment.
F-14EXPLICIT A filter box narrows the Unassigned pool by case-insensitive substring across WO # / part name / part number; the pool header shows “X of Y” while filtering, and a no-match hint when empty. Scoped to the pool only — assigned WOs under teams are unaffected. Transient (not persisted in the plan/snapshot).
F-15EXPLICIT Printing hides the Unassigned pool (@media print #pool-pane{display:none}) — a printout is the assignment board, not the intake list. (Any active filter is reflected on screen but does not affect the assigned-board printout.)

5. Data Model & Round-trip Schema

Entities use stable IDs (L#, T#, M#) so the plan CSV round-trips deterministically. Work orders are keyed by WO #.

  • Location { id, name, order }
  • Team { id, locId, name, order }
  • Member { id, teamId, name, badge (optional), order }
  • Work Order { woNo, partNo, partName, program, currentGate, ETC, percentComplete, plannedFinish, activeDrOps, asOf, ops[] (live, from feed), teamId, taggedMembers[], stale }

Plan CSV (one file, Type column): Type, Node ID, Parent ID, Order, Name, Badge, WO, Part Number, Part Name, Program, Current Gate, Planned Finish, ETC, Percent Complete, As Of, Active DR Ops, Team ID, Tagged Member IDs, Stale. Type ∈ {LOC, TEAM, MEMBER, WO}; tagged members are pipe-joined (e.g. M0|M3). Per-operation detail is not persisted in the plan (it is transient/live and re-derived from the next feed load), keeping the file lean.

7. Glossary

  • WO Assignment Feed — the PDVF §5.8 export consumed as this tool's primary input.
  • DR operation — a discrepancy/non-conformance operation, detected by operation number in the 7000–7999 range; surfaced first in Operation view.
  • Stale WO — a work order still in the plan but no longer present in the latest feed.
  • Hours-based % complete — 1 − remaining ÷ planned hours, computed by PDVF; blank when no decoder-ring labor total exists.
